# Architecture Note: Federated Deployment Path

## Rationale for Data Separation (Feature 7)

To adhere to data governance and security compliance for Central Public Sector Enterprises (CPSEs), we have separated the material catalogue into two distinct database layers:
1. **`materials_text`**: Stores the raw material descriptions, canonical attributes (type, dimension, grade), and metadata.
2. **`materials_embeddings`**: Stores the purely mathematical, one-way dense vector representations (embeddings) generated by the AI model.

### Federated Deployment Model
This split supports a hub-and-spoke federated architecture:
- **Spokes (Individual CPSEs)**: Each CPSE (e.g., ONGC, IOCL) can run the AI embedding generation entirely locally within their firewalled environment. They only ever transmit the mathematical embeddings (the `materials_embeddings` data) to the central hub.
- **Hub (Central Platform)**: The central harmonization engine receives only the dense vectors to run similarity searches. It never sees the raw, potentially sensitive `materials_text` descriptions unless explicitly authorized and shared. 

This guarantees that proprietary supply chain terminology cannot be reverse-engineered from the centralized index, addressing the primary security blocker for cloud-based procurement data pooling.
